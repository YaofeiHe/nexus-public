# 规范化需求

## 项目目标

建立一个现场事故复盘工作区，让用户能从事故发生到领导周报形成闭环：接收事故、记录事实、分析根因、指派整改、验证完成、沉淀复盘和公开摘要。

## 目标用户

- 现场协调人：提交事故 intake、影响范围和第一时间行动。
- 复盘主持人：组织时间线、根因分析和整改决策。
- 整改 owner：维护行动项、证据和验证状态。
- 领导或 PMO：阅读周摘要，识别未解决风险。

## 核心对象

- 事故记录：时间、地点、影响、严重度、当前状态。
- 证据来源：照片、日志、访谈、工单、系统指标和读取状态。
- 根因假设：问题陈述、证据支持、反证、可信度和待确认问题。
- 整改行动：owner、截止日期、验证标准、证据链接和复开条件。
- 周摘要：本周新增、关闭、阻断、升级和下周重点。

## 必须支持的 workflow

1. 事故 intake：收集事实，不急于下结论。
2. 根因复盘：把假设、证据、反证和不确定点拆开。
3. 整改验证：只有验证证据满足标准后才能关闭行动项。
4. 领导周报：输出可公开摘要和内部风险分层。

## 验收标准

- `docs/source-material-index.md` 记录每份参考材料的读取目的、状态、提取需求和未覆盖事项。
- `docs/search-plan.md` 与 `docs/search-log.md` 区分计划和结果。
- `indexes/incident-register.json` 至少包含一条完整事故样例，字段符合 `schemas/incident-review.schema.json`。
- `docs/requirement-trace.md` 能把用户纠正“例子不是范围上限”“跳过来源要记录”落到实际文件。
- `scripts/validate_project.py` 能检查事故、根因、整改、周报和公开/私有边界。

## 明确不做

- 不替代正式调查委员会或法务结论。
- 不自动发布事故公告。
- 不连接真实工单系统或监控系统。
- 不把未核实信息写入公开摘要。

## 未确认问题

- 严重度等级是否沿用现有组织标准。
- 证据附件是否需要独立文件库。
- 周报是否需要导出到飞书、邮件或 Markdown。
- 哪些事故需要强制升级到领导层。
