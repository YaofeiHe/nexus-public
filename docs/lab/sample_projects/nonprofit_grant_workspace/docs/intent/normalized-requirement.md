# 规范化需求

## 项目目标

建立一个非营利组织资助申请工作区，把资助方要求、预算、证据、材料草稿、截止日期和提交后复盘统一管理。用户需要的是可执行的申请协作系统，而不是单份申请文档。

## 目标用户

- 项目负责人：决定申请优先级，审查材料完整性。
- 项目撰写者：维护叙述材料、受益人证据和资助方匹配说明。
- 财务或运营同事：维护预算来源、限制用途和版本记录。
- 复盘负责人：记录提交结果、反馈、拒绝理由和下一次窗口。

## 核心对象

- 资助方计划：资助方名称、项目名称、金额范围、资格条件、材料清单、截止日期。
- 申请包：面向某资助方的一组草稿、附件、预算、证据和提交状态。
- 预算条目：费用类别、金额、资金来源、依据文件、是否可公开。
- 证据材料：受益人数据、访谈摘录、服务记录、授权状态、引用位置。
- 复盘记录：结果、反馈来源、拒绝理由、补充证据、下次窗口、负责人。

## 必须支持的 workflow

1. 资助方 intake：登记新资助方，拆解资格条件、材料要求、截止日期和风险。
2. 申请包构建：把预算、证据和草稿映射到资助方要求，标出缺口和负责人。
3. 截止日期与复盘：在提交前检查阻断项，提交后记录反馈并生成下一轮行动。

## 验收标准

- 原始需求全文保存在 `docs/intent/original-requirement.md`。
- 需求追踪能把用户原话中的预算、证据、截止日期、材料草稿和复盘映射到具体文件。
- `indexes/grant-pipeline.json` 可解析，且每个资助方记录至少包含要求、预算、证据、截止日期和复盘字段。
- `schemas/grant-record.schema.json` 定义资助方申请记录的必填字段和字段含义。
- `scripts/validate_project.py` 能检查文档、workflow、schema、索引和公开/私有边界。

## 明确不做

- 不自动抓取真实资助方网站。
- 不替代会计系统，不生成审计级账本。
- 不代表组织正式提交申请。
- 不把内部预算、联系人、未授权受益人信息放入公开发布材料。

## 未确认问题

- 用户是否已有历史申请材料目录。
- 资助方字段是否需要对接 CRM 或财务系统。
- 是否需要导出为 Word/PDF 申请包。
- 公开版本是否需要移除所有内部金额明细，还是只移除联系人和私有路径。
