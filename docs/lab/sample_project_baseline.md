# 样例项目通用验收基准

## 目的

这份基准用于后续生成端到端 `$nexus-workflow` 测试集，判断 Nexus 是否能把用户的初始意图转成一个可用、可维护、可验证的项目工作区。样例项目只提供验收口径，不提供可照抄的答案；任何实现都必须能覆盖同类新项目，而不是只识别某个样例名称、路径或固定文件。

本文件不定义 feeler、probe 或任何单个项目的特殊规则。它抽象的是用户对同类项目初始化、调研、构建、测试、同步和恢复的通用期望。

所有样例项目和样例外变体都必须同时接受 `scripts/lab/nexus_problem_matrix.json` 中 16 个问题轴的评测。样例不能被拆成“这个样例只测意图理解、那个样例只测同步”的单点覆盖；每个样例都要验证 Nexus 是否能把完整初始意图、读取记录、检索记录、workflow、测试反馈、同步边界、恢复回绑、playbook 和 monitor 状态组合起来。

## 通用必备基准

任一样例项目及其变体都必须具备以下产物和行为。

### 项目结构

- `docs/intent/original-requirement.md`：完整保存用户原始输入、引用路径、补充说明和约束，不改写原文。
- `docs/intent/normalized-requirement.md`：把原始输入整理成可执行需求，至少包含目标用户、项目目标、功能模块、数据对象、工作流、验收标准、明确不做的内容、未确认问题。
- `docs/project-overview.md`：面向人阅读的项目说明，必须说明项目要解决什么问题、主要模块如何配合、当前可用状态。
- `docs/requirement-trace.md`：把用户原话、参考材料、抽取出的需求、落到的文件或功能逐项对应起来。
- `docs/reference-materials.md`：列出初始化时读取或应读取的历史、文件、目录、外部材料，以及每项的读取状态。
- `docs/search-plan.md` 与 `docs/search-log.md`：记录检索目标、检索范围、命令或数据源、命中结果、未覆盖材料、下一步补查条件。
- `workflows/`：保存用户后续会实际执行的流程，例如构建、更新、测试、导出、发布、恢复。
- `schemas/` 或等价结构说明：当项目有结构化数据、记录、索引、事件或状态时，必须定义字段含义和校验规则。
- `scripts/validate_project.py` 或等价校验入口：一条命令即可检查关键文件、索引一致性、结构化数据、工作流引用、同步记录和公开安全边界。
- `.nexus/project-intent.json`：机器可读的项目意图索引，字段必须能对应到上述人读文档。
- `docs/operation-guide.md`：说明用户可执行的 `$...` 指令、默认同步规则、失败恢复方式和人工介入点。

### 需求理解产物

- 必须把“保存输入”和“理解输入”分开：原始输入只负责归档，规范化需求负责说明 Nexus 如何理解项目。
- 必须列出核心实体、用户动作、输入输出、项目边界和验收方式，不能只写一两句项目简介。
- 必须说明哪些要求来自用户原文，哪些来自参考文件，哪些是 Nexus 根据项目类型做出的推断。
- 必须标出不确定点和暂不覆盖点；不能把没有理解的内容写成已经完成。
- 如果用户提供历史文件、目录、prompt、已有项目或对照项目，必须说明它们怎样影响当前项目结构。

### 检索记录

- 检索前必须有计划：为什么查这些材料、要回答什么问题、哪些材料是必读。
- 检索后必须有记录：实际查了什么、查到什么、没查到什么、哪些材料失败或跳过、跳过原因是什么。
- 不能只给 `completed`、`blocked`、`running` 等运行状态；测试必须能看到检索计划和检索结果。
- 检索结果必须回写到需求理解和项目结构，不能只作为孤立 artifact 存在。

### Workflow

- 必须提供用户会真实使用的 `$...` 指令或等价入口，并说明每条指令会更新哪些文件、触发哪些校验、是否触发同步。
- 初始化、补充需求、调研、构建、测试、根据测试反馈修改、同步、公开发布、恢复失败必须是可追踪流程。
- 端到端测试必须能模拟多轮输入，而不是只检查初始化一次。
- Workflow 说明必须区分默认动作和显式确认动作，例如 private sync 可以默认，public 发布必须显式确认。

### 校验脚本

- 校验脚本必须检查关键文档是否存在且非占位文本。
- 必须检查原始需求、规范化需求、需求追踪、参考材料、检索记录之间是否互相引用。
- 必须检查工作流文件中提到的路径、脚本、schema 是否真实存在。
- 必须检查项目特有的结构化文件能被解析。
- 必须检查公开发布或同步相关文件不包含本地绝对路径、密钥、token、私有仓库地址、运行时 artifact 泄漏。
- 校验失败必须输出具体文件和原因，不能只返回笼统失败。

### 同步和恢复

- GitHub private 同步属于默认项目记录链，除非指令明确跳过。
- Feishu 或其他文档发布如果已配置，项目更新后应有同步记录；本地写回后不能只停留在磁盘。
- GitHub public 发布必须显式确认，并且先经过 staging、隐私扫描、可安装或可使用检查。
- 失败后如果需要外部 Codex 修复，必须保留原 `run_id`、原 pending continuation 和恢复所需状态。
- 外部修复的诊断、修改、测试、结果必须回写到原 run 的恢复记录，并在适合时沉淀到 `.nexus/recovery-playbook.json`。
- 恢复成功后必须继续原 workflow，不能新开一条看似成功但脱离原状态的链。

## 样例项目类型

### 1. 个人能力与材料工作区

适用于简历、面试、学习计划、项目陈述、作品集、职业材料等项目。样例重点是“复杂历史材料如何转成可维护工作区”。

- 项目结构：`read/`、`copy_ready/`、`file_library/`、`workflows/`、`schemas/`、`scripts/validate_project.py`，以及面向人阅读的主说明文档。
- 需求理解产物：必须说明用户当前目标、目标岗位或场景、已有材料来源、可直接复制内容、只读材料、备份材料、后续迭代入口。
- 检索记录：必须列出读取了哪些历史文件、哪些材料与当前目标相关、哪些材料只作为备份或证据。
- Workflow：至少包含材料整理、版本归档、输出同步、面试问答或复盘更新、学习或训练项目生成。
- 校验脚本：检查 copy-ready 文件和源文件是否同步，备份索引是否更新，schema 是否可解析，关键阅读文件是否存在。
- 同步/恢复：每次更新用户可读材料后要记录同步状态；失败恢复不得覆盖用户已有版本。

### 2. 可运行软件项目

适用于 CLI、Web 服务、库、自动化工具、桌面辅助工具等项目。样例重点是“意图必须落到能运行、能测试、能发布的代码结构”。

- 项目结构：`src/` 或主包目录、`tests/`、`docs/`、`scripts/`、配置样例、README、操作指南。
- 需求理解产物：必须说明核心命令或接口、输入输出、状态存储、错误处理、安全边界、部署或运行前提。
- 检索记录：如果参考现成库或已有项目，必须记录候选、取舍理由、许可证或接入风险。
- Workflow：至少包含安装、运行、单元测试、端到端测试、打包或发布、失败诊断。
- 校验脚本：检查安装、导入、CLI smoke test、测试套件、配置样例、README 命令是否可执行。
- 同步/恢复：代码变更后应触发测试和默认 private sync；外部修复必须回到原 code-change run。

### 3. 调研到实现的项目

适用于需要先研究现有工具、论文、库、公开实现，再决定复用、组合或自建的项目。样例重点是“调研不是搜索状态，而是决策证据”。

- 项目结构：`research/`、`decision_records/`、`implementation_plan/`、`src/` 或目标产物目录、`tests/`。
- 需求理解产物：必须把用户目标拆成调研问题、候选能力、必须满足的约束、不可接受的替代方案。
- 检索记录：必须保留检索计划、候选清单、可用性检查、风险、为什么选或不选。
- Workflow：至少包含调研、方案选择、实现计划、实现、验证、重新调研或换方案。
- 校验脚本：检查每个实现决策都有证据来源，候选状态不是空白，计划中的测试已执行或明确阻断。
- 同步/恢复：调研结论和实现计划更新后要同步；如果外部服务、权限或网络失败，恢复记录必须说明是否可重试、是否需要人工授权。

### 4. 文档发布与知识库项目

适用于操作指南、知识库、规则库、公开文档、内部流程手册等项目。样例重点是“文档不是散文件，而是可更新、可发布、可追踪的系统”。

- 项目结构：`docs/`、`indexes/`、`workflows/`、`publishing/`、`scripts/validate_project.py`。
- 需求理解产物：必须说明读者、文档层级、更新频率、公开/私有边界、引用来源和维护责任。
- 检索记录：必须记录从哪些历史对话、文件、规则或项目中提取内容，以及哪些内容因隐私或不确定性未写入。
- Workflow：至少包含新增文档、更新索引、发布到目标平台、公开版本生成、失效链接修复。
- 校验脚本：检查索引链接、重复章节、公开敏感信息、发布绑定记录、文档标题和路径稳定性。
- 同步/恢复：发布失败必须保留绑定状态、失败原因和恢复入口；公开发布必须经过隐私扫描。

### 5. Agent 编排与测试反馈项目

适用于 Nexus、Verix、orchestrator、skill/rule 自动化测试等项目。样例重点是“多个 agent 共享初始意图，但职责独立”。

- 项目结构：`agents/`、`testsets/`、`runs/`、`evaluations/`、`feedback/`、`workflows/`、`scripts/validate_project.py`。
- 需求理解产物：必须说明各 agent 职责、共享的初始意图、状态流、人工介入点、终止规则。
- 检索记录：必须记录 agent 生成测试前读取了哪些样例、规则、历史和项目产物。
- Workflow：至少包含样例基准提取、测试集生成、被测系统执行、独立评测、失败反馈、修改后回归。
- 校验脚本：检查测试集不是空壳，评测报告能对应到原始意图，反馈能定位到通用能力而不是样例名。
- 同步/恢复：长链路必须能查询当前状态；中途失败必须保留 run 状态，恢复后继续原编排。

## 反作弊检查

端到端测试必须主动防止 Nexus 只照样例依葫芦画瓢。

- 样例名、目录名、固定文件名不得作为特殊分支条件；测试会替换项目名、领域、路径和材料文件名。
- 测试集必须包含样例外变体，例如不同领域、不同文件组织、不同同步目标、不同失败路径。
- 评测不能只检查“文件存在”，必须检查内容是否引用了本轮新输入和本轮新材料。
- 需求追踪必须能把本轮用户原话映射到本轮产物，不能只出现样例项目里的固定短语。
- 检索记录必须包含本轮实际检索范围和结果，不能复制样例检索日志。
- 每个通用能力至少用一个正例、一个变体正例和一个反例测试；只有样例过了而变体失败时，判定为失败。
- 每个正例、变体正例和反例都要输出 16 轴 `problem_axis_results`；不能把问题轴分摊到不同样例。
- 修改 agent 的补丁说明必须指向 Nexus 的通用能力，例如初始化意图转化、检索记录生成、恢复回绑、同步链路，而不能说“专门兼容某个样例项目”。
- 如果输出中出现样例专属名称、路径、历史文件或固定结构，而本轮输入没有提供这些材料，判定为样例泄漏。

## 端到端测试使用方式

测试集生成 agent 使用本基准生成 `$nexus-workflow` 指令，不直接生成 Nexus 代码补丁。

1. 按上述五类项目生成 3-5 个高质量样例，再为每类生成至少 2 个样例外变体。
2. 为每个项目生成多轮 `$nexus-workflow` 指令：初始化、补充需求、检索/调研、构建或更新、测试、同步、故障恢复。
3. 执行 agent 在隔离 workspace 和独立运行数据目录中真实运行 Nexus，保存 `interaction.json`、`state.json`、tool results、项目文件和同步记录。
4. 评测 agent 按本基准检查产物，不只看 Nexus 是否返回成功状态。
5. 失败报告必须写成通用能力缺口：缺哪个产物、哪条输入未被理解、哪次检索无记录、哪条同步或恢复链路绕开了统一规则。
6. 修改 agent 只能根据失败报告修改 Nexus 的通用实现；修改后必须重跑样例和变体。
7. 通过标准是：样例项目和样例外变体都能达到同类质量，且同步、公开发布、恢复和 playbook 沉淀行为符合本基准。
